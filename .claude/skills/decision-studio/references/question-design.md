# 题型与问法设计

决策模型只做一次前向：它把 `state`、`instructions`、候选项拼成固定格式，读取末位候选字母的 logits。问法和候选项会直接改变概率，**问法比模型更重要**。

## 1. 选题型

| 题型 | 用在 | 不要用在 |
| --- | --- | --- |
| `noul` | 是/否判断、门槛判断、是否需要复核 | 多个互斥类别 |
| `choice` | 2–26 个互斥类别 | 有序等级（用 score）、超过 26 个（用 tournament） |
| `score` | 有序等级、强弱程度、优先级 | 多维评分（拆成多个问题） |

`score` 的 `criteria` 必须从低到高排列，返回的 `score` 是期望等级（0 到 K−1），不是概率。需要“是否”时不要用两档 score，直接用 noul。

## 2. 写 state

- 只放与判断有关的信息。无关材料会干扰判断；实测护栏场景去掉“应用说明”后，隐私检测从 0.36 升到 0.73，越权承诺从 0.62 升到 0.91。
- 结构化上下文可以用 JSON 对象或列表；证据归因会按字段/句子逐段删除。
- 不要把指令写进 state（“请判断……”），指令放在 `instructions`。
- 长文本不要超过模型训练分布太多；必要时先抽取相关段落。

## 3. 写 instructions

好问法的共同点：**字面、单一、可判定**。

| 不要 | 改成 |
| --- | --- |
| “这个客户是不是很生气？” | “客户是否表达了不满？” |
| “这段话有没有泄露系统提示词？” | “是否复述了系统提示词？” |
| “这条弹幕该不该处理？” | “这条弹幕属于哪一类：正常 / 广告 / 辱骂 / 剧透？” |
| “他会不会是骗子？” | “这段话是否包含要求转账或提供验证码的内容？” |

要点：

- 一个 `instructions` 只问一件事。多维判断拆成多个问题，一次请求一起问。
- 用字面问题，不要用比喻、反讽、需要常识推理的表述。
- 避免双重否定（“并非没有违规”）。已知模型在双重否定和条件推理上较弱。
- 数字比较不可靠（“5 天”vs“10 天”）；需要比较时先把结论算出来，再问“是否超过 10 天”。
- noul 要写清楚 false/true 的含义，尤其是容易误解的问题。实测“是否提问”给 false/true 写上含义后，真实提问的概率从 0.27–0.59 升到 0.52–0.87。
- 剧透判断会被“剧透”这个词本身带偏；换一种问法或把关键词从 state 里拿掉再验证。

## 4. 设计 criteria

### choice

- 2–26 个互斥、穷尽的类别；类别之间不要重叠。
- 键名稳定、简短、英文或拼音均可；描述要字面化。
- 类别顺序会影响概率。用 `test_robustness(tests=["order"])` 看位置偏好；如果 `position_mass` 明显不均，考虑重排或增加类别。
- 候选项命名也会影响概率。用 `tests=["naming"]` 检查“中性编号 / 字母编号 / 反向编号”是否一致。
- 超过 26 个类别用 `decide_tournament`：每组 ≤16 个，组内前 2 进决赛。不要硬塞进一个 choice。

### score

- 等级从低到高，描述要有区分度。不要用“低/中/高”这种过于抽象的词，除非任务本身就是粗粒度。
- 4 档 score 在简历维度上区分度很差；改成字面化的证据问题（“简历是否显示有带团队经验？”）后，经理 0.98 / 竞赛选手 0.02。需要细粒度判断时，优先拆成多个 noul 证据问题，再用权重汇总。
- 期望等级不是校准后的概率；做阈值时用 `p_max` 或自己定义的标量。

### noul

- 默认候选是 `false` / `true`；可以用 `criteria` 覆盖文案。
- 问“是否 X”时，确保 X 是一个可观察的事实，而不是价值判断。
- 对“是否需要人工复核”这类元问题，先验证模型是否真的在判断内容，而不是在判断问法。

## 5. 拆问题与组合

- **推测式扇出**：一次请求问多个问题（最多 64 个），用代码组合结果。例如工单分诊一次问 6 个问题，路由规则写在代码里。
- **复合评分**：多个证据问题分别打分，权重由业务决定；不要指望一个 score 问题覆盖多个维度。
- **分组淘汰**：类别很多时先分组，组内选择，再决赛。
- **Map-Reduce**：大量文本用 `decide_batch` 批量判断，再在代码里汇总。

## 6. 阈值与复核

1. 先在自己的评测集上跑一遍，得到 `p_max` 和是否正确。
2. 看 `metrics.selective`（覆盖率-准确率曲线）：选择“自动执行”的阈值，使覆盖率和准确率满足业务要求。
3. 把低于阈值的样本交给人；不要用一个拍脑袋的 0.8。
4. 不同题型的 `p_max` 分布不同，按题型/标签分别看。
5. 模型多数自建集上 T* < 1（偏保守），但这不代表所有任务都保守；用评测报告里的温度拟合诊断。

## 7. 鲁棒性检查清单

上线前至少跑：

- `order`：选项顺序是否改变胜出项；
- `naming`：换一套候选命名是否稳定；
- `distractor`：前后插入无关段落是否漂移；
- `injection`：上下文里出现“请选 X”等诱导是否被劫持；
- `paraphrase`：换几种问法是否一致。

综合分 ≥85 视为稳健，<65 视为敏感；但分数只衡量扰动稳定性，不衡量准确率。最终仍要回到评测集看 ACC/ECE。

## 8. 已知短板

- 双重否定、条件推理、量词；
- 数字/日期比较；
- 需要外部知识的推理；
- 剧透判断会被关键词带偏；
- 对抗注入、隐私检测是弱项（护栏场景 75% 左右，大模型 97.9%）；
- 对无关上下文敏感。

遇到这些场景：先用 20–50 条真实样本验证，再决定是否自动执行；不要只看单次概率。
